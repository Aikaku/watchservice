## 1단계. 탐지 엔진 다듬기 (03-06 ~ 03-11)

### 1-1. 피처 계산 개선 — "랜섬웨어가 이렇게 움직이면 놓친다"

방법은 매번 같았다. **실제 랜섬웨어의 행동 패턴을 하나씩 떠올리고, 현재 코드가 그 패턴을 잡는지 확인했다.** 못 잡는 경우가 개선 항목이 됐다. 이 내용은 `FEATURE_CHANGES.md`에 개선 1~9로 정리돼 있다.

| # | 놓치던 상황 | 원인 | 해결 |
|---|-------------|------|------|
| 1 | 파일 중간·끝부터 암호화하는 랜섬웨어 | 엔트로피를 앞 4096바이트만 읽어서 계산 | `computeMultiSectionEntropy()` — `SeekableByteChannel`로 앞 40% / 중간 40% / 끝 20% 샘플링 |
| 2 | `file.doc → file.doc.wncry` (WannaCry·LockBit의 전형) | rename 매칭 점수가 0점 | 확장자 덧붙이기 패턴 +3점, 파일명(stem) 동일 +2점 |
| 3 | 처음 보는 파일이 이미 암호화된 상태로 생성됨 | 비교할 before 스냅샷이 없어서 판정 불가 | 엔트로피 ≥ 7.2 + 의심 확장자면 encrypt-like로 판정 |
| 4 | 암호화 신호가 평균에서 희석됨 | 엔트로피 변화 ≈ 0인 이벤트까지 평균에 포함 | 변화량 0.05 초과만 평균에 반영 |
| 5 | 모든 파일을 같은 확장자로 바꾸는 공격 | 의심 확장자의 "개수"만 봄 | 같은 의심 확장자가 3개 이상이면 flag=1 |

03-11에는 크로스 플랫폼 정확도를 다시 점검했다.

| # | 문제 | 해결 |
|---|------|------|
| 6 | `.json`, `.html`, `.java` 같은 흔한 파일이 "의심 확장자"로 오탐 | whitelist를 14개에서 33개로 확장 |
| 7 | 암호화 복사본을 CREATE해도 writeCount가 늘지 않음 | 4KB 이상 CREATE도 write로 집계 |
| 8 | RC4 같은 스트림 암호는 크기·확장자가 그대로라 탐지 불가 | "엔트로피↑ MODIFY → 같은 경로 DELETE" 순서를 감지 |
| 9 | NIO는 READ 이벤트를 주지 않아 fileReadCount가 과소 추정됨 | "삭제하려면 먼저 접근해야 한다"는 논리로 DELETE를 접근 증거로 포함 |

> 개선 9의 효과 예시: 파일 50개를 읽고 삭제하는 랜섬웨어 패턴에서 fileReadCount가 **0에서 50으로** 바뀌었다.

### 1-2. 멀티유저 데이터 분리 — 문제 발견 → 리팩터링 → 빌드 오류 → 수정

- **문제**: `SessionIdManager`가 싱글톤이고 `session_id.txt`에서 UUID 하나를 읽어 썼다. 그래서 **모든 사용자가 같은 ownerKey를 공유**했고, 사용자끼리 데이터가 섞였다.
- **해결 방향**: HTTP 세션마다 UUID를 발급해서 `HttpSession`의 `OWNER_KEY` 속성에 저장한다(`OwnerKeyUtil`).
  - `EventWindowAggregator`에 `UserWindowState`, `WatcherService`에 `UserWatcherState`를 만들어 사용자별로 상태를 분리했다.
  - Service 5개와 Controller 7개에 `ownerKey` 파라미터를 추가했다.
- **커밋 흐름** (하루에 4번 커밋):
  1. `웹 동시 사용자 가능 환경으로 변경`
  2. `웹 동시 사용자 환경 개선 2차 (추가 작업 요망)` — 아직 미완성 상태
  3. `웹 동시 사용자 추가 구현`
  4. 마무리하면서 **빌드 오류 3건** 발견:
     - `ScanService`에서 `startWatchingMultiple()` 호출 시 ownerKey 누락
     - 관리자 화면은 특정 사용자가 아니라 전체 상태를 봐야 하는데 `isRunning(ownerKey)`만 있었음 → `isAnyRunning()` 추가
     - `AdminSystemController` 컴파일 오류 → `isAnyRunning()`으로 교체
- **결과**: `BUILD SUCCESSFUL`
- **후일담**: 이 구조는 05-18에 다시 바뀐다 ([바뀐 결정들](#바뀐-결정들--만들었다가-되돌린-것) 참고).

### 1-3. Gemini API 연결 — 문제 4개를 차례로 해결 (03-08)

"Gemini가 정말 동작하는가?"를 확인하는 과정에서 문제가 하나씩 나왔다.

| 순서 | 증상 | 원인 추적 | 해결 |
|------|------|-----------|------|
| ① | AI 서버 없이는 Gemini만 따로 테스트할 방법이 없음 | — | `GET /ai/gemini/test` 테스트 엔드포인트 추가 (LockBit 시나리오 고정) |
| ② | `.env`에 키를 넣었는데도 키가 없다고 나옴 | `start.sh`가 `.env`를 셸에 로드해도 **Gradle `bootRun`은 셸 환경변수를 JVM에 넘기지 않음** | `build.gradle`에 `bootRun { environment System.getenv() }` 추가 |
| ③ | `Read timed out` | Gemini 응답이 약 2.7초인데 타임아웃 기본값이 2.5초 | 타임아웃 2500 → 10000ms |
| ④ | 답변이 몇 줄 만에 잘림 | Gemini 2.5 Flash의 **thinking 토큰**이 `maxOutputTokens=400` 중 대부분을 써버림 | `maxOutputTokens` 1500으로 늘리고 `thinkingBudget: 0`으로 thinking 비활성화 |
| ⑤ | 고친 뒤에도 가끔 키가 없다고 나옴 | 키 없이 떠 있던 **기존 Gradle 데몬이 재사용됨** | `bootRun --no-daemon` |

- **커밋**: `제미나이 API 연결 관련 설정 추가` → `Gemini API 연결 모드 및 토큰, 타임아웃 수정`
- **검증**: `curl http://localhost:8080/ai/gemini/test` → LockBit 대응 가이드가 정상 생성됨

### 1-4. 상용화 준비 점검 → 보안 강화 (03-08 ~ 03-09)

코드 전체를 점검해서 상용화 전에 해야 할 일을 P0~P3로 분류하고 위에서부터 처리했다.

### 2-1. `api_server.py`를 직접 읽고 버그 찾기

처음에는 `코드/` 폴더 전체를 읽기 전용으로 정했다. 그런데 `api_server.py`를 분석해 보니 **직접 고쳐야 하는 버그**가 있었다. 그래서 CLAUDE.md 규칙에 이 파일만 편집을 허용하는 예외를 추가하고 수정했다.

| 문제 | 구체적 예시 | 해결 |
|------|-------------|------|
| **score 계산 오류** | `LockBit=0.30, WannaCry=0.28, benign=0.42`면 top-1이 benign이라 **SAFE**로 판정. 실제로는 랜섬웨어 확률 합이 0.58이라 WARNING이 맞음 | benign이 아닌 모든 클래스 확률을 합산. 0.70 이상 DANGER, 0.50 이상 WARNING, 미만 SAFE |
| `/health`가 거짓으로 정상 응답 | 모델 로드에 실패해도 200 `ok:true` → 탐지가 안 되는데도 아무도 모름 | 모델이 없으면 503 반환 |
| 죽은 코드 | `fillna(-1)` — 이미 -1로 채운 뒤라 효과 없음 | 제거하고 이유를 주석으로 남김 |
| 누락 피처를 -1로 채움 | 9개 피처는 모두 개수·평균이라 -1은 의미 없는 값 | 기본값 0 |
| AI 서버 CORS가 `["*"]` | 백엔드만 호출하는 내부 서버인데 누구나 호출 가능 | 환경변수로 받고, 기본값은 `localhost:8080` |

- **커밋**: `AI 연결 api 문제 확인 및 수정` → `api 고정값 오류? 수정` (CORS, 기본값 0)

## 3단계. 데스크탑 앱으로 전환 (03-24 ~ 03-30)

### 왜 전환했나
- React(3000)와 Spring Boot(8080)가 따로 떠서 CORS 처리가 필요했다.
- 사용자가 Java와 Node를 직접 설치하고 터미널로 실행해야 했다. **일반 사용자에게는 진입 장벽이 너무 높았다.**

### Phase별 진행

### 4-2. 안정성 작업 11건 (04-07) — 진행률 60% → 83%

| 문제 | 해결 |
|------|------|
| BCrypt를 도입했는데도 평문 비밀번호를 넣으면 **평문 비교로 우회됨** | 평문 폴백 제거. BCrypt 해시가 아니면 로그인 차단 |
| API 오류 시 Spring 기본 HTML 에러 페이지가 반환돼 프론트에서 파싱 불가 | `GlobalExceptionHandler` (404 / 400 / 500을 JSON으로) |
| `path=../../etc/passwd` 같은 입력을 검증하지 않음 | Bean Validation (`@NotBlank`, `@Pattern`, `@Size`) |
| 운영 환경 CORS 기본값에 Vite 개발 서버(5173)가 포함됨 | 기본값에서 제거 |
| 일반 사용자 API에 인증이 없음 | 선택형 사용자 인증 (`USER_AUTH_ENABLED`, 기본값 false) |
| AI 응답이 지연되면 로딩이 끝나지 않음 | 모든 fetch에 10초 타임아웃 (`AbortSignal.timeout`) |
| 컴포넌트 하나의 오류로 앱 전체가 흰 화면 | `ErrorBoundary` |
| URL을 직접 입력하면 관리자 화면이 렌더링됨 | `ProtectedRoute` / `UserProtectedRoute` + `/api/admin/check` |

#### 응답 형식 통일 → 설정 기능이 통째로 고장 → 원인 추적 → 수정
1. **API 응답 형식 통일**: 컨트롤러 6개를 `ApiResponse{success, data, message}`로 감쌌다. 기존 프론트 코드를 고치지 않아도 되도록 `HttpClient.js`가 `data`를 자동으로 꺼내게 했다.
2. **증상**: 이후 감시 폴더 목록이 빈 배열로 나오고, 폴더 탐색 모달에도 아무것도 표시되지 않았다.
3. **원인**: `SettingApi.js`만 `HttpClient.js`를 쓰지 않고 **자체 `fetch` 함수**를 쓰고 있었다. 그래서 자동 unwrap이 적용되지 않았고 `{success, data, message}`가 그대로 넘어와 훅에서 `[]`로 폴백됐다. 쿠키 설정도 빠져 있어 인증을 켜면 401이 나는 문제도 숨어 있었다.
4. **해결**: `SettingApi.js` 전체를 `HttpClient`의 `get`/`post`/`put`/`del`로 다시 썼다.
- **커밋**: `API 응답 방식 통일 작업` → `진행상황표 최신화, 누락항목 추가 및 버그 즉시 수정`

### 4-3. 추가 기능 2차 (04-09) — 진행률 83% → 93%
- **소리 알림 ON/OFF**: 설정에서 꺼도 소리가 계속 났다. `AudioAlert`가 설정값을 읽지 않고 있었다. `localStorage` 설정값을 읽도록 연동했다.
- **수동 스캔 결과 모달**: 스캔이 끝나도 아무 표시가 없었다. 스캔한 파일 수를 보여주는 모달을 추가했다.

- **감시 폴더 자체의 삭제 감지**: NIO는 등록한 폴더 *안쪽* 이벤트만 알려준다. 그래서 **부모 디렉토리도 감시**하고, 루트 폴더가 사라지면 AI를 거치지 않고 바로 DANGER로 처리했다.

- **랜섬웨어 패밀리 상세 정보**: 패밀리 13종 JSON과 상세 모달 (05-14에 제거).

#### 코드 검토 중 발견한 숨은 버그 — YAML 들여쓰기

**① "서비스 시작 실패" 팝업**

**② 흰 화면 (White Screen)**

### 6-3. "서비스 시작 실패" 원인을 알 수 없는 문제 (05-14)
- 증상: Windows에서 7~8초 만에 실패 팝업이 떴다. 메시지는 항상 같았다.
- 단서: 7~8초는 JVM이 뜨다가 **포트 8080 충돌**로 죽는 시간과 일치했다.
- 해결: 원인을 구분해서 보여주도록 했다.
  - 시작 전에 TCP bind를 시도해서 포트가 비어 있는지 확인한다.
  - stderr에서 `already in use`를 감지한다.
  - `error.html?reason=port|crash|timeout`으로 원인별 메시지를 보여준다.

### 6-4. 이메일 테스트 발송이 "성공"이라고 거짓으로 표시됨 (05-14)
- 원인 1: `@Async` 때문에 컨트롤러가 실제 발송 전에 200을 돌려줬다. 그래서 **SMTP가 없어도 "발송 완료"**로 표시됐다.
- 원인 2: SMTP가 설정되지 않으면 조용히 return했고, 발송 오류는 catch에서 삼켰다.
- 원인 3: `.env`에 SMTP 자격증명이 아예 없었다.
- 해결: 테스트 발송은 동기로 실행하고, 실패하면 예외를 던져 프론트가 "발송 실패"를 표시하게 했다. Gmail 앱 비밀번호를 설정했다.

### 7-2. 빌드 자체가 안 됨 — Java 25 문제 재발
- 증상: `Unsupported class file major version 69`
- 원인: 시스템 기본 JDK가 **Java 25**(클래스 파일 버전 69)로 바뀌어 있었고, Gradle의 Groovy 컴파일러가 이를 읽지 못했다. 03-09에 `start.sh`로 피했던 문제가 빌드 스크립트 경로에서 다시 나온 것이다.
- 해결: `gradle.properties`에 `org.gradle.java.home`을 Java 17로 고정했다.
  - 이 줄은 05-08에 Windows 빌드 때문에 지웠던 줄이다. **Mac과 Windows가 같은 설정 파일을 두고 충돌**하고 있었다. Windows 쪽은 `WINDOWS_BUILD.md`에 `JAVA_HOME`을 직접 지정하는 절차로 정리했다.

### 7-3. 인수테스트 버그 4건 (오전)

| 이슈 | 원인 | 해결 |
|------|------|------|
| 탐지해도 대시보드가 갱신되지 않음 | `loadSummary()`를 마운트 때 한 번만 호출 | `useCallback`으로 빼고 5초 폴링 |
| 긴급 경보의 "확인" 버튼이 동작하지 않음 | `contextIsolation: true` + preload 없는 창에서는 `window.close()`가 막힘 | preload를 연결하고 IPC `close-emergency-window`로 닫음 |
| 다른 페이지에 갔다 오면 "감시 시작" 버튼으로 돌아감 | `isWatching`이 컴포넌트 state라 재마운트되면 초기화 | `GET /watcher/status` 추가, 마운트 때 서버 상태로 복원 |
| AI 대응 가이드가 매번 같음 | Gemini 키가 없을 때의 `fallbackGuidance()`가 고정 문자열 | 등급·점수·파일 수·감지 행동을 넣은 동적 가이드로 변경 |

### 7-4. Gemini 키가 설치본에서 읽히지 않음
- 원인: `.env`는 개발할 때 `bootRun`에서만 쓰였다. **Electron이 JAR를 실행할 때는 `.env`를 전혀 읽지 않았다.**
- 해결:
  1. `build.gradle`의 `bootRun`이 `.env`를 직접 파싱한다.
  2. Electron `main.js`에 `loadDotEnv()`를 추가해서 패키지 resources의 `.env`를 읽고 `spawn`할 때 `env`로 넘긴다.
  3. (15:39) `package.json`의 `extraResources`에 `.env`를 넣어 설치본에도 포함되게 했다.
- 추가로 Gemini 타임아웃의 코드 기본값이 2500ms로 남아 있어서 15000ms로 올리고, 토큰 사용량 로그를 추가했다. 프롬프트도 **비전공자용 6항목 체크리스트**(임의로 삭제하지 말 것, 몸값을 지불하지 말 것 등)로 다시 썼다.

### 7-5. 긴급 전체화면 경보가 뜨지 않음
- 원인 1: `main.js`의 폴링은 Node `http` 모듈로 **쿠키 없이** 요청했다. 그래서 서버가 새 세션과 새 ownerKey를 발급했고, 프론트 세션에 저장된 DANGER 알림을 볼 수 없었다.
- 원인 2: `page=1`을 보내고 있었는데 Spring `Pageable`은 0부터 시작하므로 **2페이지를 조회**하고 있었다.
- 해결: `session.defaultSession.cookies`에서 `JSESSIONID`를 가져와 헤더에 넣고, `page` 파라미터를 지웠다.

### 7-6. 시나리오 재검토로 나온 버그

### 7-7. DANGER 이메일이 오지 않음 — 4단계로 추적

테스트 이메일은 오는데 실제 DANGER 알림 이메일만 오지 않았다.

| 단계 | 시각 | 가설 / 한 일 | 결과 |
|------|------|--------------|------|
| 1 | 16:37 | **추적할 로그가 없음** → `NotificationService`에 `@Slf4j`와 DANGER 발생 시 ownerKey/email 로그 추가. 발송을 건너뛰는 이유를 `debug`에서 `warn`으로 올림 | 원인 단서 확보 |
| 2 | 16:49 | 단서: **서버를 재시작하면 인메모리 세션이 사라져 새 UUID ownerKey가 발급됨.** 이메일 주소는 예전 키에 저장돼 있고 알림은 새 키로 저장되니 이메일을 찾지 못함 → **단일 사용자 데스크탑 앱이므로 ownerKey를 `"default"`로 고정** | 이메일 조회는 성공. 그래도 발송 안 됨 |
| 3 | 17:05 | `@Async` 안에서 `mailSender.send()`가 던지는 `MailException`(RuntimeException)이 `catch (MessagingException)`에 걸리지 않아 **조용히 사라짐** → `@Async` 제거, catch 범위를 `Exception`으로 확대 | 실패가 로그에 보이기 시작 |
| 4 | 17:46 | 테스트 발송과 DANGER 발송의 차이는 **`buildHtmlBody(notification)`** 하나뿐이었음. 알림 객체의 필드에 접근하다 예외가 나고 있었음 → **이미 잘 동작하던 테스트 발송과 같은 고정 HTML**로 교체 | 해결 |

> 비교해서 찾는 방법이 통했다. "되는 경로(테스트 발송)와 안 되는 경로(DANGER 발송)의 차이"를 하나씩 없애 가니 원인이 좁혀졌다.

## 돌아보며 — 반복해서 나온 문제 유형

1. **"개발 환경에서는 되는데 설치본에서는 안 된다"**
   - `.env` 미전달(bootRun → Electron), 헬스체크 503, SPA 포워딩과 정적 파일 충돌, 서명 문제.
   - → 설치본으로 직접 인수테스트를 돌린 뒤에야 드러났다.
2. **실패가 조용히 사라지는 코드**
   - `@Async` + 좁은 catch, undefined 함수 호출, 조용한 return, 거짓 200 응답(`/health`, 테스트 이메일).
   - → 로그 추가와 "실패하면 예외를 던지기"로 해결했다.
3. **세션·식별자 불일치**
   - Electron 폴링과 브라우저 세션이 서로 다른 ownerKey를 받음, 재시작 후 ownerKey 변경, Pageable 0-index.
4. **리팩터링 후 남은 호출부**
   - `pickFolderPath`, `promptAndAddFolder`, `SettingApi.js` 미마이그레이션.
   - → 이름이나 구조를 바꿀 때 호출하는 곳 전체를 검색해야 한다.
5. **환경 차이 (Mac ↔ Windows, Java 버전)**
   - Java 25 문제 2번, `gradle.properties` 경로 충돌, winCodeSign 심볼릭 링크, Windows 경로·드라이브 처리.
6. **문서와 실제 동작의 차이**
   - 수동 스캔 / 즉시 검사, 진행률 과소 기록, 이미 구현된 기능을 "예정"으로 표기.
   - → 시나리오를 쓰면서 실제 화면과 하나씩 대조해서 바로잡았다.
